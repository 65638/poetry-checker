## 12. 核验脚本的 5 条硬规矩（踩坑记录，D3 补）

本仓库的核验脚本出过 5 次**假阳/假阴**，全部可复现。下面每条都写明真因与正确做法——
**按成因分类，不要笼统归给"PowerShell 问题"**，否则下次会查错地方。

### 12.1 中文 JSON 一律用 node 或 `Get-Content -Raw -Encoding UTF8`

- 真因：PowerShell 的 `Get-Content` **默认按 GBK 解码**。
- 后果：中文变乱码 → `ConvertFrom-Json` 直接抛 `ArgumentException` → 误判"文件损坏"。
- 正确：`Get-Content -Raw -Encoding UTF8`，或直接用 node（UTF-8 直读）。
- 归属：核验工具坑（实测踩过：读 `d3-a-candidate-batch` 时 `$b.entries[0]` 报 `NullArray`）。

### 12.2 不要用 `@($obj.missingField).Count` 判字段存在性

- 真因：PowerShell 对 `$null` 包装后 `.Count` 可能是 **1**。
- 后果：字段实际不存在，却得出"字段非空"的假阳。
- 正确：node 用 `'key' in obj`；PowerShell 用 `$obj.PSObject.Properties.Name -contains 'key'`。
- 归属：核验工具坑（实测踩过：`positions` 字段存在性）。

### 12.3 比较对象/计数表时不要用 `JSON.stringify` 比键序

- 真因：`JSON.stringify` 保留对象键的插入顺序，**键序不同即判不等**（与语言无关的 bug）。
- 后果：`bucketCounts` 实测与门槛**内容完全相同**却被判"不符"，凭空造出一条 P1 假异常。
- 正确：按 key 排序后逐键比较（`sameCounts()`），或直接比有序数组。
- 归属：**脚本 bug**，不是工具坑（实测踩过：xinyun 分部计数误报）。

### 12.4 产物字段名/类型必须对着「交付接口草案」断言，不能只断言"值对不对"

- 真因：`positions` 曾写成单数 `position`(串)，值全对但键名不符草案。
- 后果：下游 `entry.positions` 读到 `undefined`，整批对照**空转**却无任何报错。
- 正确：加断言覆盖**字段存在性 + 类型 + 元素非空**，不只覆盖业务值。
- 归属：接口 bug（实测踩过：D3 Gate 1 批次，已由 `d5940c2` 修）。

### 12.5 统计「去重字形数」一律用 node（Ordinal 语义），不要用 PowerShell 的 `-Unique`

- 真因：`Select-Object -Unique` / `Sort-Object -Unique` / `HashSet(CurrentCulture)`
  走**文化比较**（`StringComparer.CurrentCulture`），会把**补充平面字**（surrogate pair，
  UTF-16 占 2 码元）与形近 BMP 字判为相等而静默并掉。
- 实测：同一份 `pingshui.full-d2-patched.json`
  ```
  node new Set             → 8240   ← 正确
  Select-Object -Unique    → 8238
  Sort-Object -Unique      → 8238
  HashSet(StringComparer.Ordinal)       → 8240   ← 用对比较器即可
  HashSet(StringComparer.CurrentCulture) → 8238
  被并掉的字：𪻐 U+2AED0、𫘤 U+2B624（均为 surrogate pair）
  ```
- 后果：**静默少计，不报错**。更危险的是被并掉的是**有真实归部的韵字**——
  `𪻐` 在快照里有 `二冬` / `三江` 两条候选，并掉等于静默删字。
- 正确：node `new Set(chars)`；必须用 PowerShell 时改
  `[System.Collections.Generic.HashSet[string]]::new([System.StringComparer]::Ordinal)`。
- 归属：核验工具坑（实测踩过：A1 字符全集曾被外部核验为 8238，据此差点改错统计）。

### 12.6 通用推论

以上 5 条指向同一条工作方式：**核验脚本本身也要被核验**。
凡是"数字对不上"的场合，先确认**测量口径**（编码 / 比较器 / 字段存在性 / 键序），
再怀疑数据；反之，凡是"看起来全绿"的场合，先确认断言**覆盖了字段存在性与差额**，
再相信结论。
