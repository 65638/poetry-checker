## 2. A/B要先交给你什么

一个批次最多一张摘要表，正文材料可机器化展开：

| 必有字段 | 要回答的问题 |
|---|---|
| batchId＋文件SHA256 | 你确认的究竟是哪一份、之后是否被改过 |
| 具体book/candidateId集合与计数 | 是否只是指定范围，有没有暗中扩大成整韵部 |
| 固定来源/修订/字节哈希/定位 | 能否回到相同原文，许可证与正确性是否分开 |
| AI检查与交叉复核结果 | 哪些只是字形匹配、哪些有语义/音读依据 |
| 异常清单及推荐项 | 哪些真正需要你裁定，选项的依据与影响是什么 |
| 排除范围 | 哪些竞争候选、其他书、全库仍不批准 |
| 接收后的实际动作 | 追加独立候选依据/限定语境规则/重建版本，不是全局改标记 |

无异常候选由AI完成初审和独立交叉检查，你可以接受该**固定批次**，无需逐字肉眼复核。语义冲突、简繁归并、来源矛盾、关键多音、音系映射等异常由你按摘要裁定；依据仍不足可以选“保留待核”。

## 3. 你可以怎样回复

以下只是未来回复示例，**当前没有替你作出这些确认**：

```text
接受批次 d3-a-001（摘要以本次提供的 SHA256 为准）中的无异常候选。

范围仅限清单候选和已写明的语境，不批准整部或全库。
```

如果不想当场处理异常，可以只接受明确列出的无异常范围，其余保持待核；A/B继续独立工作。每轮只集中提交新增异常，已批准条目不反复打扰。

## 4. A/GLM必须怎样记

登记文件草案（这是审核记录，不改HTTP契约）：

```json
{
  "reviewId": "d3-review-实际编号",
  "batchId": "d3-a-001",
  "batchSha256": "真实文件摘要",
  "actualReply": null,
  "method": "接受AI初审批次并人工裁定异常",
  "acceptedCandidateIds": [],
  "exceptionDecisions": [],
  "excludedScope": ["整部批准", "全库发布", "未列举候选"],
  "status": "awaiting_decision"
}
```

actualReply为空表示未收到确认，不能据此设置Evidence为approved。实际回复到达后按原话及精确范围记录；记录为接受AI初审，不写“组长逐字肉眼核验”。变更批次内容必须重新形成版本及差异，不能确认后悄悄追加候选。

已有审批原件保持字节不变，尤其已被SHA引用的文件；更正或补充用新记录关联原文件，避免让可追溯链失效。

## 5. 全库发布单独判断

三库结构106/19/14齐全只是第一关。全库发布还需要有效批准范围覆盖、引用/来源闭合、版本可复现、内容异常处理及可解释限制。不能为了readyz200一口气把快照改approved，也不能把词林/新韵仍503当可选功能。

D3先把九组合及异常账跑实；若完整发布证据还不齐，D4继续主线修复，并向用户界面和演示材料如实说明可用范围。半天彩排是D5硬保留，不以全库审核为由无限推迟。
